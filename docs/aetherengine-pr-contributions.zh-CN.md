## 先理解两个词

- **硬解**：主要用设备专门的视频芯片播放，通常更省电。
- **软解**：主要用 CPU 播放，某些问题视频更容易兼容，但可能更耗性能。

## 第一部分：较早的 10 个 PR

### 1. [#411：修复某些 MP4 从开头就抖动](https://github.com/superuser404notfound/AetherEngine/pull/411)

- **原问题**：视频里的“每张画面什么时候显示”记录错了，看起来会前后抖动，即使网速足够也没用。
- **本 PR 的修改**：识别这类文件，改用软解和另一套画面时间信息，让画面按正常顺序显示。
- **直观作用**：让这类从开头就抖动的视频恢复正常观看；原方案可能增加 CPU 开销。
- **状态**：已关闭，被 [#413](https://github.com/superuser404notfound/AetherEngine/pull/413) 的另一种修法替代。维护者采用了本 PR 的识别思路和测试素材，但选择直接修正时间信息、保留硬解，并非原方案直接合并。

### 2. [#419：继续修复上一轮没修好的抖动视频](https://github.com/superuser404notfound/AetherEngine/pull/419)

- **原问题**：有些视频每帧的时间间隔不是完全相等，而是有规律地长一点、短一点，旧修复认不出来。
- **本 PR 的修改**：从实际时间记录中找出重复规律，恢复正确的显示时机，而不是简单套用固定帧率。
- **直观作用**：让这类帧间隔有规律变化的视频也能按正确节奏显示，减少抖动。
- **状态**：已关闭，核心诊断被维护者采纳，用另一套实现合入 [#427](https://github.com/superuser404notfound/AetherEngine/pull/427)。

### 3. [#510：解决部分视频拖动进度后持续卡顿](https://github.com/superuser404notfound/AetherEngine/pull/510)

- **原问题**：某些 H.264 视频正常播放没事，一快进或后退，就一直像低帧率幻灯片。
- **本 PR 的修改**：先确认它属于特定编码结构，再自动改走软解兼容路线。
- **直观作用**：让这类视频拖动后还能正常看。代价是可能更耗 CPU，不是所有视频都改软解。
- **状态**：仍开放，尚未合并。

### 4. [#511：修复某些 MKV 的画面显示顺序](https://github.com/superuser404notfound/AetherEngine/pull/511)

- **原问题**：文件把“机器处理画面的顺序”当成“观众看画面的顺序”，导致画面抖动、时间倒退。
- **本 PR 的修改**：根据视频内容中的真实顺序，把已有的显示时间重新分配给对应画面，不修改原视频文件。
- **直观作用**：恢复这类 MKV 的正常画面顺序，减少抖动和时间倒退。
- **状态**：已关闭，但诊断和测试证据被采纳。维护者换成等待更少、兼容性更稳的实现，已随 6.74.0 发布。

### 5. [#512：让软解也能真正保留缓存，拖回去不用重下](https://github.com/superuser404notfound/AetherEngine/pull/512)

- **原问题**：软解播放时，已经下载的内容不能很好地用于来回拖动，缓存进度也容易一拖就消失。
- **本 PR 的修改**：把下载和播放分开，暂存下载好的压缩音视频数据；拖到仍在缓存里的位置，就直接读取，没缓存才重新向服务器取。
- **直观作用**：缓存范围内的快进、后退更少重复下载，缓存进度也更可信。不是永久离线下载。
- **状态**：已合并。

### 6. [#513：修复“前面正常，后面开始抖”的 MP4](https://github.com/superuser404notfound/AetherEngine/pull/513)

- **原问题**：有些文件开头的画面时间正确，后半段却损坏。旧逻辑检查开头正常，就认为整部都正常。
- **本 PR 的修改**：播放过程中继续识别后面的问题段，只修复证据充分的异常部分，正常部分不动。
- **直观作用**：避免看着看着，或者拖到后半段，突然出现持续抖动。
- **状态**：已合并。

### 7. [#533：修复拖动后图片字幕消失](https://github.com/superuser404notfound/AetherEngine/pull/533)

- **原问题**：播放器显示的时间和视频文件内部时间不一定从同一个起点开始；重建播放后，可能跑到错误时间去找字幕。
- **本 PR 的修改**：正确保留两套时间之间的换算关系，让字幕继续对应当前画面。
- **直观作用**：某些 MKV 的 PGS 图片字幕，在快进、后退或重建播放后不再凭空消失。
- **状态**：已合并。

### 8. [#759：让缓存条更真实，拖动失败也别假装成功](https://github.com/superuser404notfound/AetherEngine/pull/759)

- **原问题**：缓存信息可能只反映最远下载位置，无法说明哪些部分还能回看；读取出错可能连累已有内容；拖动失败可能被当成成功；远程定位等待时间也可能不足。
- **本 PR 的修改**：包含以下几项相关改进。

  1. 准确告诉 App 哪些时间段真的还在缓存里，包括可以回看的部分，而不只是显示“最远下载到哪里”。
  2. 网络读取出错后，仍保留已经完整存好的可用内容，不把它们一起判废。
  3. 快进、后退没成功，就明确报告失败，不把进度条摆到目标位置后假装已经播到了。
  4. 给慢但仍有进展的远程定位更多等待时间，相关定位预算由 8 秒调整为 30 秒，但不保证总操作一定在 30 秒内完成。

- **直观作用**：缓存条更可信，已缓存内容更耐受网络错误，拖动失败也能让 App 正确处理。
- **状态**：已合并。

### 9. [#761：补上两类更复杂的画面时间修复](https://github.com/superuser404notfound/AetherEngine/pull/761)

- **原问题**：有些视频开头帧间隔会变化；另一些视频的画面先后关系更复杂。之前的修复条件太窄，仍会漏掉它们。
- **本 PR 的修改**：利用更多实际画面顺序证据，扩大能正确识别和修复的范围，仍保留原有时间信息，不随便按平均帧率重造一套。
- **直观作用**：让此前修不好的一部分 MP4 也能平顺播放，正常视频不受影响。
- **状态**：已合并。

### 10. [#785：解决某些视频快进或重新打开后“有声音、没画面”](https://github.com/superuser404notfound/AetherEngine/pull/785)

- **原问题**：视频中途改变了分辨率等编码参数，播放器却还拿开头的旧参数处理，可能只剩声音。
- **本 PR 的修改**：检测实际参数变化，必要时自动切换到兼容的播放路线，并尽量留在用户正在看的位置，而不是跳到后台预下载的位置。
- **直观作用**：这类视频遇到黑屏时能够恢复画面；切换期间可能短暂缓冲，也可能改用更耗性能的软解。
- **状态**：已合并。

## 第二部分：最近提交的 12 个 PR

### 11. [#821：暂停时，缓存进度也继续更新](https://github.com/superuser404notfound/AetherEngine/pull/821)

- **原问题**：视频暂停后，后台还在下载，但 App 收到的缓存进度不更新，看上去像停止缓冲了。
- **本 PR 的修改**：暂停期间也定时报告真实缓存位置。
- **直观作用**：不用先点播放，就能看到已经缓冲到哪里。它是修正进度显示，不是提高下载速度或扩大缓存。
- **状态**：已合并。

### 12. [#822：别把视频服务器的认证信息自动发给别的字幕网站](https://github.com/superuser404notfound/AetherEngine/pull/822)

- **原问题**：下载外挂字幕时，可能自动带上视频请求里的认证等信息，即使字幕来自另一个网站。
- **本 PR 的修改**：默认只在协议、主机和端口相同的情况下沿用这些信息；其他字幕服务器需要 App 明确指定。
- **直观作用**：减少认证信息被误发给其他服务器的风险。这是一项安全边界修复。
- **状态**：已合并。

### 13. [#823：遇到极端错误的音频时间数据，不要直接崩溃](https://github.com/superuser404notfound/AetherEngine/pull/823)

- **原问题**：内核计算“这段声音覆盖多少时间”时，遇到特别离谱的时间数值，减法可能超出数字范围，导致崩溃。
- **本 PR 的修改**：先检查能不能安全计算；算不了就拒绝采用这段结果，不再硬算。
- **直观作用**：提高异常文件下的稳定性，也避免把不可靠的范围当成可直接跳转的缓存。
- **状态**：仍开放。当前分支还包含 #831，本文将两者的主要贡献分开说明。

### 14. [#824：切换音轨后，第二条字幕别丢设置或选错语言](https://github.com/superuser404notfound/AetherEngine/pull/824)

- **原问题**：内部重建播放时，第二条外挂字幕只记住了网址，可能忘记选的是里面哪种语言，以及访问它需要哪些认证信息。
- **本 PR 的修改**：按完整的字幕登记信息恢复，同时拦住旧影片迟到的字幕结果，防止它串到新影片。
- **直观作用**：双字幕在切换音轨、重新加载时更可靠。
- **状态**：已合并。原说明整理时仍开放，2026-10-21 保存前重新核验时已更新为合并。

### 15. [#825：给两路图片字幕补测试，防止互相串台](https://github.com/superuser404notfound/AetherEngine/pull/825)

- **原问题**：文档还说第二路只支持文字字幕，但代码其实已有独立处理部分图片字幕的能力，相关保护测试不够完整。
- **本 PR 的修改**：字幕部分仅纠正文档并补测试，检查两路 PGS 图片字幕的颜色、位置、清除和拖动后恢复是否互不干扰。
- **直观作用**：防止后续修改把已有双字幕能力改坏。重点是“验证已有能力”，不是这次才新加双图片字幕；App 仍要负责把两路字幕画出来。
- **状态**：仍开放。当前分支还包含 #832，分段下载改动另见该项，不重复计为字幕功能。

### 16. [#826：第二条 ASS 字幕也能保留字体、位置等样式信息](https://github.com/superuser404notfound/AetherEngine/pull/826)

- **原问题**：ASS 字幕自带样式和布局说明，主字幕能保留，副字幕却可能丢掉这部分信息。
- **本 PR 的修改**：副字幕也遵守保留样式的设置，并单独提供自己的样式说明，不与主字幕混用。
- **直观作用**：让 App 有足够的信息正确显示第二条带样式字幕。它提供数据，不等于内核已经替 App 完成全部样式绘制。
- **状态**：仍开放。

### 17. [#827：让 App 自己选择缓存放内存还是磁盘](https://github.com/superuser404notfound/AetherEngine/pull/827)

- **原问题**：软解缓存主要按平台默认策略选择位置，App 不方便明确指定。
- **本 PR 的修改**：增加“自动、内存、磁盘”三种选择。
- **直观作用**：App 开发者可以按设备和需求调整。默认不变：tvOS 自动模式仍用内存，其他平台仍用磁盘；也不是自动给用户界面加了一个设置按钮。
- **状态**：仍开放。

### 18. [#828：别把连续的声音缓存误判成中间缺一小块](https://github.com/superuser404notfound/AetherEngine/pull/828)

- **原问题**：音频本来连续，但文件记录时间时有取整，比如一段记成 46 毫秒、下一段 47 毫秒。简单计算会误以为中间有缝。
- **本 PR 的修改**：在能确认格式和采样规律时，按照真实声音采样节奏判断连续性，同时仍然识别真正缺失的数据。
- **直观作用**：减少“明明已经下载了，却说这个位置没缓存、不能直接跳过去”的情况。它修的是缓存判断，不是改变声音或提升音质。
- **状态**：仍开放。

### 19. [#829：换外挂字幕前先检查，坏字幕别把正在用的字幕顶掉](https://github.com/superuser404notfound/AetherEngine/pull/829)

- **原问题**：用户选了一个新字幕，可能先撤掉旧字幕，随后才发现新文件打不开或解析失败。
- **本 PR 的修改**：增加“先准备、确认可用后再切换”的接口。准备失败，旧字幕继续保留；已经过时的选择也不能迟到后覆盖新选择。只准备已在本地的字幕文件，不负责下载。
- **直观作用**：字幕切换更稳，不会因为选到坏文件而把原来的字幕也弄没。需要 App 接入这个新接口。
- **状态**：仍开放；依赖并包含 #826 的副字幕样式信息支持。

### 20. [#830：让 App 能规定临时缓存大小，并知道清理是否成功](https://github.com/superuser404notfound/AetherEngine/pull/830)

- **原问题**：App 能设置一些缓冲策略，却不方便指定精确的字节预算，也难知道缓存实际占多少、停止后是否清理成功。
- **本 PR 的修改**：增加缓存容量预算和状态查询，包括实际占用、是否因满额暂停下载、清理结果等。
- **直观作用**：便于 App 做缓存管理和故障说明。
- **边界**：这是临时点播缓存，不是跨次打开仍保留的离线影片。预算并非硬上限，必要的播放工作区可能超过设定值，设为 0 也不等于完全不读写。
- **状态**：仍开放。

### 21. [#831：文件已经全部预下载，就别再额外请求文件尾部](https://github.com/superuser404notfound/AetherEngine/pull/831)

- **原问题**：小文件已经完整放进预热缓存，但打开时仍可能再向服务器请求一次结尾数据。
- **本 PR 的修改**：确认整个文件都已在缓存里，就跳过这次多余请求；只缓存了一部分的文件，仍照常补齐需要的内容。
- **直观作用**：减少重复网络请求和不必要的流量，不是取消正常的文件尾部读取。
- **状态**：仍开放。

### 22. [#832：下载缓冲已经满了，就先别请求下一段视频](https://github.com/superuser404notfound/AetherEngine/pull/832)

- **原问题**：分段视频下载中，一段刚好下载完时，缓冲区已经满了，却可能继续请求下一段，绕过本来应该等待的检查。
- **本 PR 的修改**：每次发起下一段请求前，先确认缓冲区还有空间；播放消耗掉一些数据后，再继续。加密视频的相关密钥请求也纳入检查。当前片段仍完成下载，在发下一段请求前等待，不截断当前下载。
- **直观作用**：让下载按缓存承受能力进行，避免满了还继续往里塞；停止或切换后也不能继续发旧请求。
- **状态**：已采纳并随 7.43.0 发布。维护者把提交重新放入 `main`，所以原 PR 显示“关闭、未合并”，并不代表没采用。

## 怎样理解这些贡献

这些 PR 主要围绕三件事：让问题视频能正常看，让缓存和拖动更可靠，让双字幕更稳定、更安全。

- **22 个是提交数量，不是 22 项完全独立功能。** #823 的当前分支还包含 #831，#825 包含 #832，#829 包含 #826。本文按各自主要贡献说明，避免重复计算。
- **“已合并”不等于播放器 App 已升级或已经用上。** 是否生效仍取决于 App 当前依赖的内核版本、是否接入相应接口，以及字幕绘制等 App 自身实现。
- **历史方案和最终实现需要分开理解。** #411、#419、#511 的诊断或测试证据被采纳，但维护者选择了替代实现；#832 则是重放提交进入主线。应结合各项状态理解实际落地方式。
